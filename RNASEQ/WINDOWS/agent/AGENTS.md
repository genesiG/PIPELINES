# AGENTS.md — RNA-seq project (Rephill Lab), Docker version for Windows

This folder is **one lab member's RNA-seq project**, run with the lab's shared pipeline (Docker version for Windows)
installed on this computer at:

    {{PIPELINE_DIR}}

You are here to help this user run the pipeline on *their* data, check results, and customize *their* analysis. The
user is usually a wet-lab scientist: do the technical work, explain in plain language, and ask them for what only they
know. You are not here to change the pipeline itself.

The pipeline counts the reads of each library per gene (HISAT2 alignment, duplicate marking, featureCounts) and merges
the counts into one table. It can also run a DESeq2 **differential expression** analysis on that table (`run_deg: true`, off by default; see "Differential expression" below). Otherwise differential expression comes later, from the table in `results\counts\`.

## Hard rules

1. **Never edit anything in the pipeline folder above** (or anywhere in its git clone) unless the user explicitly asks
   to change the **lab-wide** pipeline. To change how this project's analysis works, use a per-project override (see
   "Customizing").
2. **Only launch the pipeline with this project's `utils\run_rnaseq.bat run`, and run this project's own analysis
   scripts with its `script` command** (see "Analyses beyond the pipeline"). Don't call `docker run`, `nextflow`,
   `hisat2`, `samtools`, `featureCounts`, `Rscript`, `python`, or the pipeline's `bin\` scripts yourself. The launcher
   handles Docker, the input checks, logging and resuming. Never call `RUN_ANALYSIS.bat` (it's the double-click launcher
   for humans and waits for a key press).
3. **Don't run analysis work on the computer itself.** Reading logs, CSVs and other small text files is fine. Opening
   FASTQ or BAM files, or running any analysis, is not: that goes through `script` (or `run`), where the pipeline's image
   and memory limits apply.
4. **The raw FASTQs and BAMs are the user's data.** They stay where the user keeps them: the paths in `config.yaml` and
   `samplesheet.csv` point to them, and the launcher reads them in place, read-only. Never move, copy, rename, delete or
   overwrite them. `fastq_dir` is not used by this version: leave it `null`.
5. **Ask before destructive or expensive actions:** deleting `results\`, `intermediate_files\` or `metadata\`; `clean` (it
   deletes `metadata\work\` and `metadata\.nextflow\`); changing `keep_work`; or launching a run when nothing has changed.
   A full run takes hours and a lot of disk.
6. **Don't hand-edit files in `results\` or `intermediate_files\`.** They are regenerated by the pipeline; change the
   inputs or an override instead.
7. **Don't guess data paths.** FASTQ, BAM, HISAT2 index and GTF paths come from the user. Ask.
8. **Never change `strandedness` on your own.** The strandedness check reports what the libraries look like; it never
   changes the counts. Whether the configured value is right is the user's decision (see "Strandedness" below).
9. **The computer's settings are the user's.** Don't edit `%USERPROFILE%\.wslconfig` by hand, don't change Docker
   Desktop's memory limit, and don't install software (on the computer or inside the container at run time) without
   asking. When the launcher asks about Docker's memory limit, answer only with the user's OK; don't add `--yes` on your
   own.

## Ask about the experiment; never assume it

You know the pipeline; only the user knows the experiment. Before you prepare inputs, choose a strandedness, interpret
results, or write Methods or figure text, ask the user for the context below, unless they already gave it in this
conversation or it is in `CONTEXT.md`. Ask even when it seems obvious.

- **The question:** what the experiment is meant to show, and which genes they expect to change or not to change
  (positive and negative control genes).
- **The RNA and the library:** the source, the extraction, the library kit and protocol, poly-A or total RNA, and whether
  the library is **stranded** (this decides `strandedness` in `config.yaml`).
- **Each sample:** the treatment, dose and timepoint; which samples are biological replicates and which are technical;
  and anything that went wrong (low input, a failed library, a re-sequenced sample). Which samples to exclude.
- **The sequencing:** paired-end or single-end, the read length, which run(s) and lanes, and whether the FASTQs are
  already demultiplexed. This pipeline version supports paired-end data only; say so if the data are single-end.
- **The comparisons:** which treatment-vs-control comparisons answer the question. The pipeline does not make them yet.

- Ask in short batches (3-6 questions at a time), in plain language, and say why each answer matters. Keep asking until
  the answers are specific; "the usual" or "like last time" is not an answer, so ask what it was.
- **Never infer the design from names** (`A`/`B`, `rep2`, `ctrl`, `DMSO`, `1uM`, `KO`) or from what is "typical" for
  RNA-seq. Ask what each name means.
- Use only what the user confirmed. Where an answer is missing, say what you would do instead and wait for an explicit
  OK; never fill the gap silently, and never pick controls, replicates or comparisons yourself.
- **Write the answers down** in `CONTEXT.md` in the project folder (dated, in the user's words, with open questions marked
  as open). Read it at the start of every session; ask the user to confirm it is still right before you rely on it, and
  add to it as you learn more. It is tracked by git with the inputs.
- **When the data seem to contradict the stated context, flag it; don't reinterpret.** Examples: a strandedness `mismatch`
  (`results\qc\strandedness\strandedness.tsv`); an overall alignment rate below `alignment_min_pct`
  (`results\qc\hisat2\alignment_summary.tsv`). Show the user the numbers and the file they come from, say what the data
  would be consistent with, and ask. The user's description stands until they change it.
- Subagents cannot talk to the user: put the confirmed context (or the path to `CONTEXT.md`) in every brief, and pass
  their "Questions for the user" back to the user rather than answering them yourself.

## Running

From this folder (PowerShell):

```powershell
& .\utils\run_rnaseq.bat run --detach    # start (or resume) the analysis; returns immediately
& .\utils\run_rnaseq.bat status          # running / succeeded / failed + step counts + last log lines
& .\utils\run_rnaseq.bat logs            # follow the live log (Ctrl+C stops watching; the run goes on)
& .\utils\run_rnaseq.bat stop            # stop; the next run resumes
& .\utils\run_rnaseq.bat clean           # delete metadata\work and the resume cache (asks first)
```

(From Git Bash: `cmd.exe //c utils\run_rnaseq.bat status`.) A different config file: `run --detach other.yaml`.

The analysis runs inside Docker Desktop, in the background: closing the terminal doesn't stop it, but the computer must
stay awake. Docker Desktop must be running; the launcher starts it if needed (it can take a minute or two).

Re-running is always `utils\run_rnaseq.bat run` again. Resuming is built in, so any step whose inputs, script and
settings haven't changed is reused. Only what changed, and anything downstream of it, re-runs. There is no "run just
step X" command: change the thing, re-run, and caching does the rest.

Nextflow's work folder is `metadata\work\` and its resume cache is `metadata\.nextflow\` (with `work_volume: false`; with
the default `work_volume: true` they are in the project's Docker volume, and `status` shows its name). `keep_work` in
`config.yaml` defaults to `true`: they are kept, so a re-run resumes and only redoes what changed. With
`keep_work: false` they are deleted after a successful run, and re-running then recomputes everything. Failed or stopped
runs always keep them. `publish_mode` defaults to `auto`: files in `results\` are hard links or copies of the work files,
so big files are not stored twice. Never edit a published file in place (replacing or deleting is fine).

First time on a computer: Docker Desktop and the pipeline's software image are a one-time setup. Ask the user first, then
run `& "{{PIPELINE_DIR}}\run_rnaseq.bat" setup` (it installs Docker Desktop with winget if it is missing, after asking, and
downloads the image; a restart may be needed). `setup` also prints the versions of the image's tools. Then, in a new
project: `& "{{PIPELINE_DIR}}\run_rnaseq.bat" init "<folder>"`. `init` creates the folder layout, fetches the templates,
these agent files and the `.claude\agents\` kit, and rewrites the two launchers. It never overwrites `config.yaml`, the
samplesheet or the agent files.

If `utils\run_rnaseq.bat` here fails with "cannot find the path", the pipeline folder moved: re-run
`& "<new pipeline folder>\run_rnaseq.bat" init "<this folder>"`.

## Input files

### samplesheet.csv: one row per library

```
sample_id,fastq_1,fastq_2,bam,exclude,<any metadata columns>
```

| Column | Meaning |
|---|---|
| `sample_id` | Unique library name, used verbatim in file names; letters, digits, `.`, `_`, `-` only (`^[A-Za-z0-9._-]+$`). No read suffix (no `.R1`). |
| `fastq_1`, `fastq_2` | Paths of the R1 and R2 FASTQ (paired-end only). Give both, or give `bam` instead. |
| `bam` | Path of a BAM. It is converted back to paired FASTQ first (BAM_TO_FASTQ), and the FASTQs then go through the normal steps. Give a FASTQ pair or a BAM for each row, not both. |
| `exclude` | `true` drops the row from the whole run; blank or `false` keeps it. Excluded rows stay in the file. |
| metadata columns | Free (for example `condition`, `cell_line`, `treatment`). Copied into `results\samplesheet.tsv` for later analysis; they change nothing in the counts. |

Rules enforced at startup (the run stops with a message): `sample_id` is present and unique and matches the pattern; each
row has either a FASTQ pair or a BAM (not both, not neither); both FASTQ files of a pair are given; every listed file
exists; no duplicate column header; at least one row is not excluded. Comments (`#` lines) are not allowed in the CSV.

### Input paths on Windows

- Write paths in full (`D:\data\x_R1.fastq.gz`) or relative to this folder (`original_data\x_R1.fastq.gz`). Forward
  slashes also work (`D:/data/x_R1.fastq.gz`).
- A Windows drive named in `config.yaml` or in the samplesheet of this folder is mounted **read-only** inside the
  analysis (as `/mnt/<letter>`, e.g. `D:\x\y` is read as `/mnt/d/x/y`). Nothing is copied from it. The drive must be
  connected when the run starts, or the launcher stops before anything runs.
- **Network paths (`\\server\share\...`) are refused.** Map the share to a drive letter (File Explorer: This PC > Map
  network drive) and write the path with that letter.
- The output folders `outdir`, `metadata_dir` and `intermediate_dir` must be relative (`./results`, `./metadata`,
  `./intermediate_files`); a drive path there is refused.
- Only `config.yaml` and the samplesheet in the project folder itself are checked and mounted. Keep the samplesheet there.
- `metadata\host_paths.tsv` lists every translated path, as written and as used. Check it when a path looks wrong.
- Reference files on this lab PC are in `D:\REFERENCES`. This is an **example layout**, not a requirement; ask the user
  for their own files:

```yaml
hisat2_index: D:\REFERENCES\hisat2\t2t\chm13-2   # HISAT2 index PREFIX (T2T-CHM13)
gtf: D:\REFERENCES\genomes\t2t\t2t.ncbiRefSeq.curated.norandom.gtf   # featureCounts GTF and the RSeQC gene model
```

## Key config choices (config.yaml; every key has a default)

- `project_name`, `samplesheet`, `hisat2_index`, `gtf` (the last two have no default).
- **Strandedness**: `strandedness` (`unstranded` default, the legacy setting; `forward`; `reverse`) sets featureCounts
  (`-s 0`, `1`, `2`). The automatic check (`strand_call_threshold` 0.8, `infer_experiment_reads` 200000) only reports.
  Changing it re-counts every library: ask the user first.
- **Trimming** (Trimmomatic): `trim` (true), `trim_adapter_set` (`TruSeq3-PE-2`), `trim_illuminaclip`
  (`2:30:10:8:True`), `trim_steps` (empty), `trim_minlen` (25). `trim: false` passes the reads through unchanged.
- **Alignment** (HISAT2): `hisat2_args` (empty) is added to the pipeline's own options; `alignment_min_pct` (50) is the
  warning level for the alignment rate (it warns, never fails). Changing alignment settings re-runs the alignment: ask.
- **Filtering**: `mapq` (30; `0` = no filter). `remove_chroms` (empty = keep all contigs; `chrM` reproduces the legacy
  BAMs and changes no count on the T2T annotation, but zeroes the mitochondrial genes on mouse: keep it empty for mm39).
- **Duplicates**: `mark_duplicates` (true: marked, and counted; false: no metrics), `remove_duplicates` (false: legacy;
  true removes them before counting: changes the counts, ask first),
  `optical_duplicate_pixel_distance` (2500).
- **Counting** (featureCounts): `featurecounts_feature_type` (`exon`), `featurecounts_attribute` (`gene_id`),
  `featurecounts_args` (empty). Changing one changes the counts: ask first.
- **QC switches**: `run_fastqc` (true), `run_multiqc` (true).
- **Run bookkeeping**: `keep_work: true` (default), `work_volume: true` (default), `publish_mode: auto` (copies with the
  work volume), `publish_intermediates: false` (default; `true` publishes the trimmed FASTQs and the BAMs to
  `intermediate_files\`).
- **Resources (optional)**: `max_cpus` and `max_memory_gb` lower the run's budget (see "Memory" below).
- **`wsl_resize: false`** leaves Docker's memory limit alone (Windows only).
- `fastq_dir` stays `null`.

## Memory and Docker's memory limit (this computer)

- **Run budget.** The most one analysis may use is the smallest of: 75% of the computer's memory (always leaving 3 GB to
  Windows), what Docker Desktop may use (its memory limit, minus a little for its own system), and the most the pipeline
  can put to use (`max_useful_memory_gb` in `docker\requirements.conf`). CPU cores: all but one or two. `max_memory_gb`
  and `max_cpus` in `config.yaml` lower the budget (they cannot go above Docker's limit). The run log banner states the
  budget and why. The budget must be at least `min_memory_gb` (`docker\requirements.conf`); below that the run refuses
  to start, with a plain message.
- **Docker's memory limit.** Docker Desktop's VM memory is the `memory=` line of `[wsl2]` in
  `%USERPROFILE%\.wslconfig`. Before a run the launcher sets it by the computer's RAM: under 12 GB, 6 GB; 12 to under 24 GB,
  8 GB; 24 GB or more, 16 GB. It asks first (Y/N; the user's answer decides), restarts Docker Desktop (about a minute), and
  puts the old value back when the analysis finishes, or at the next `run_rnaseq` command if the window was closed early.
  It changes the limit only when no other container is running; otherwise it leaves the limit as it is and says so.
  `--no-wsl-resize` on the command line, or `wsl_resize: false` in `config.yaml`, turns this off. The launcher marks its
  change in `.wslconfig`; leave that file to it.
- The heaviest step is the alignment (ALIGN). A step killed for running out of memory (exit 137) is retried with more
  memory, within the budget (see "When a run fails").

## Monitoring a run

```powershell
& .\utils\run_rnaseq.bat status                                          # the summary; use this
Get-Content (Get-ChildItem metadata\nf_logs\nextflow_*.log | Sort-Object Name | Select-Object -Last 1) -Tail 50
Import-Csv metadata\pipeline_info\execution_trace.txt -Delimiter "`t" | Select-Object name,status,exit
```

`status` says `RUNNING`, or `last run succeeded`, `last run failed (exit N)`, `last run interrupted` (Docker or the
computer stopped mid-run: just run again) or `last run stopped by the user`. A finished run is also written in
`metadata\nf_logs\last_run.status` (`succeeded` or `failed (exit N)`). Poll every few minutes.

## When a run fails

1. `& .\utils\run_rnaseq.bat status` names the failed step and its exit status, and the folder
   `metadata\failed_tasks\<timestamp>\` with the failed step's files.
2. Read `metadata\failed_tasks\<timestamp>\<step>\`: `command.sh` (what ran), `command.err` and `command.log` (what it
   said), `exitcode`, `workdir.txt`. For a step that *succeeded*, the same exact command is saved next to its results:
   every `log\` folder has a `<sample>_<step>_command.sh`.
3. Common cases:
   - **Exit status 3** is a known data problem; it is not retried and the message says what to fix. Typical: an empty
     BAM (ALIGN); a BAM with no read pairs (BAM_TO_FASTQ); no contig left after `remove_chroms` (BAM_FILTER); a
     strandedness output without the fraction lines (INFER_STRANDEDNESS); an empty per-sample count table
     (FEATURECOUNTS); a gene column that differs between samples (COUNTS_MERGE).
   - **Exit status 137, 140, 143** (out of memory or killed): retried automatically with more memory. If a step still
     fails, report it to the user.
   - **Startup errors** (the message names the column, the sample or the key): fix it in the project folder, then run.
   - **Join or "Join mismatch" messages at the end of the log** are usually a side effect of an earlier abort: read the
     first ERROR in `metadata\nf_logs\nextflow_<timestamp>.log`.
4. Fix the input or config, then run `run --detach` again. Completed steps are reused.
5. If the failure looks like a bug in the shared pipeline rather than in this project's data or config, **tell the user and
   stop**. Do not patch the pipeline folder.

## Differential expression (run_deg)

`run_deg: true` adds the DEG steps after the counts. Needed: `deg_comparisons` (CSV: `model`, `design`, `comparison` and one contrast per row:
`factor`+`numerator`+`denominator`, or `coef`, or `add`[+`subtract`]) and sample metadata with the design columns (`deg_metadata`, or the
samplesheet's own columns). Optional: `deg_heatmaps`, `deg_colors`, `deg_label_rules` (CSVs), `deg_reference_levels`
(`treatment=LUC_DMSO,drug=DMSO`), and the `deg_*` parameters in README.md ("Differential expression"; the template is `examples/config.yaml`).
To run only the DEG steps on an existing counts table, set `deg_counts` as well: no reads, references, QC or MultiQC are needed.
Results are in `results\deg\` (`prepared\`, `qc\`, `<model>\<comparison>\results_<comparison>.csv`, volcano plots, heatmaps, `gene_plots\`).

Choosing the comparisons, the design, `deg_alpha`, `deg_lfc` or the shrinkage is a scientific decision: tell the user and ask. Exit status 3
of a DEG step is a data problem (an unknown factor level, a design that is not full rank, a count column without metadata); the message
says what to fix.

An interaction model, or any other custom statistical test, is not part of the pipeline: it goes in a custom script in the project's `utils\`
folder. Such a script can read `results\deg\prepared\counts_edited.rds` and `sample_metadata_edited.rds`; run it with `run_rnaseq script utils\X.R`.
Do not write it unless the user asks, and the choice of model is theirs.

## Strandedness

`strandedness` (unstranded, forward or reverse) sets how featureCounts counts: unstranded `-s 0`, forward `-s 1`,
reverse `-s 2`. The default `unstranded` is the legacy GG setting. The automatic check (RSeQC `infer_experiment.py` on a
sample of reads per BAM) writes `results\qc\strandedness\strandedness.tsv` with the fraction of reads explained by each
strand orientation, the call (forward, reverse or unstranded, by `strand_call_threshold`), the configured value, and a
`mismatch` column (true when the call differs from the configured value). A mismatch prints a warning at the end of the
run and nothing else happens: the counts are not changed.

When the check reports a mismatch, tell the user the numbers from that table and ask which library preparation was used.
Changing `strandedness` is their decision; re-running after the change re-counts every library (featureCounts is re-run,
the alignment is not).

## Customizing this project's analysis

Every step of the pipeline runs one script from `{{PIPELINE_DIR}}\bin\`. To change a step for this project only, copy that
script into `utils\`, edit the copy, and add a `config.yaml` line **named after the script** (file name without extension)
with the copy's path. The shared script stays untouched for everyone else.

```powershell
Copy-Item "{{PIPELINE_DIR}}\bin\featurecounts.sh" utils\          # 1. copy
# 2. edit utils\featurecounts.sh (keep Unix line endings: LF); keep its header's arguments and output file names
# 3. add to config.yaml:   featurecounts: utils/featurecounts.sh
```

Add `<script name>_args: "..."` to pass extra arguments to a shipped script. `.py` scripts run with `python3`, `.R` with
`Rscript`, anything else with `bash`.

Scripts (= the `config.yaml` key that replaces each): `bam_to_fastq.sh`, `fastqc.sh`, `trim.sh`, `align.sh`,
`alignment_summary.py`, `bam_filter.sh`, `mark_duplicates.sh`, `gtf_to_genepred.sh`, `genepred_to_bed12.sh`,
`infer_strandedness.sh`, `qc_strandedness_table.py`, `featurecounts.sh`, `counts_merge.py`, `samplesheet_tsv.py`,
`multiqc.sh`, and for the DEG steps `deg_common.R` (helpers), `deg_prepare.R`, `deg_qc.R`, `deg_deseq2.R`, `deg_results.R`, `deg_transform.R`, `deg_volcano.R`, `deg_heatmap.R`, `deg_ma.R`, `deg_gene_plot.R`.

Some keys are both a switch and a script name: `trim` and `mark_duplicates`. A `true` or `false` value is the switch; a
path is a replacement script. Anything that changes the counting method (the featureCounts options, the duplicate policy,
the MAPQ filter, the strandedness) is a scientific decision: tell the user and get confirmation first.

Duplicates are marked, not removed (default), and featureCounts counts every read in the marked BAM, duplicates included.
That is the legacy behaviour and a deliberate choice of the user; say so if you summarise the counts.

## Disk space

The launcher checks the free space before each run: it takes the total size of the FASTQ and BAM files named in the
samplesheet and compares it with the factors in `{{PIPELINE_DIR}}\docker\requirements.conf` (`disk_factor`,
`disk_results_factor`), for Docker's disk (the work files) and for the project's drive (the results). It warns when the
free space is short, and stops before the run below 20 GB free on the project's drive (`disk_hard_min_gb`). These factors
are estimates pending the next run. To estimate by hand, add up the sizes of the files named in the samplesheet:

```powershell
Import-Csv samplesheet.csv | ForEach-Object { $_.fastq_1; $_.fastq_2; $_.bam } |
  Where-Object { $_ -and (Test-Path -LiteralPath $_) } |
  ForEach-Object { (Get-Item -LiteralPath $_).Length } | Measure-Object -Sum |
  ForEach-Object { '{0:0.0} GB of input files' -f ($_.Sum / 1GB) }
```

The working files and the results take the rest. To free space, once the user is happy with the results:
- `& .\utils\run_rnaseq.bat clean` (ask the user first; it asks too): removes `metadata\work\` and `metadata\.nextflow\`.
  Results are kept; the next run starts from scratch.
- or `keep_work: false` in `config.yaml`: they are deleted after each successful run.

Failed or stopped runs always keep them, so a re-run resumes.

## Subagents

The subagent definitions are in `.claude\agents\` of this project (copied there by `init` when the pipeline has them).
Delegate with the same table as `CLAUDE.md`; every task in it goes to its agent:

| Task | Agent | Model |
|---|---|---|
| Messy input files (Excel/CSV sample sheets, `samplesheet.csv`, collaborator or core tables) | `input-preparer` | sonnet |
| Reading: a question needing >2 files, or a file over ~300 lines | `scout` (several in parallel) | haiku |
| After every run, success or failure | `log-inspector`, then `results-reporter` on success | haiku |
| Comparing with earlier, benchmark or collaborator numbers | `output-verifier` | haiku |
| Statistics questions, counting choices and any design beyond counts | `statistician` | sonnet |
| Plots | `figure-maker` | sonnet |
| Analysis beyond the pipeline (see "Analyses beyond the pipeline") | `statistician` (design), `code-supervisor` (script), `log-inspector` (script log), `methods-writer` | sonnet / haiku |
| Methods text | `methods-writer` | sonnet |
| Edits to `utils\` scripts or the samplesheet beyond a trivial fix | `code-supervisor` (spawns `implementer`) | sonnet |
| Writing or editing code that `code-supervisor` hands over | `implementer` | haiku |
| Outside facts (tool flags, library formats) | `web-researcher` | haiku |
| Papers and citations | `literature-scout` | sonnet |
| How HISAT2, featureCounts, RSeQC or the pipeline code works | `code-researcher` | sonnet |

Rules for every subagent:

- Read-only in the pipeline folder `{{PIPELINE_DIR}}`; never edit `original_data\`, or any raw FASTQ or BAM.
- Never start, stop, clean or resume a run, and never run a `script`: only the lead does that, with `utils\run_rnaseq.bat`.
  The Hard rules apply to subagents too (no `docker run`, `nextflow`, `hisat2`, `samtools`, no `Rscript` or `python` on the
  computer).
- Files they change are in this project. Git is the backup: the lead commits after asking the user.

If the agents are not listed as available subagent types (e.g. the project was created mid-session), either spawn a
general-purpose agent whose prompt is the agent file's body (after the frontmatter) plus the brief, with the model from the
file's frontmatter, or ask the user to restart Claude Code in the project folder (recommended for every later session:
start Claude Code inside the project folder, so it loads this project's `CLAUDE.md` and agents).

If `.claude\agents\` is missing, this project predates the kit: `init` of a newer pipeline version creates it, or copy
`{{PIPELINE_DIR}}\agent\.claude\agents` here (`Copy-Item -Recurse`).

## Documentation

- `{{PIPELINE_DIR}}\README.md`: the user's documentation for this Windows version (parameters, the samplesheet, the outputs,
  the benchmark check).
- `{{PIPELINE_DIR}}\ANALYSIS.md`: what each step does, the tool versions to cite, and how to read the outputs.
- `{{PIPELINE_DIR}}\SETUP.md`: the one-time setup of the computer.
- Windows-specific behaviour (paths, the launcher, the memory and disk rules) is in this file.
