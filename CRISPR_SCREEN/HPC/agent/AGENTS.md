# AGENTS.md — CRISPR screen project (Richard Phillips Lab)

This directory is **one lab member's CRISPR screen project**, run with the lab's
shared Nextflow pipeline at `/project/rephilllab/CRISPR_SCREEN/HPC`. You are here to
help this user run the pipeline on *their* data, check results, and customize
*their* analysis. You are not here to change the pipeline itself.

## Hard rules

1. **Never edit anything under `/project/rephilllab/`** (`CRISPR_SCREEN/`,
   `bin/`, `nf_containers/`) unless the user explicitly asks to change the
   **lab-wide** pipeline. Every lab member runs those files. To change how this
   project's analysis or plots work, use a per-project override (see
   "Customizing"), never an edit to the shared copy.
2. **Only launch the pipeline with `run_crisprscreen.sh`.** Don't call
   `nextflow`, `mageck`, `cutadapt`, `Rscript` or `python` analysis scripts
   yourself, and don't `bsub` your own jobs. `run_crisprscreen.sh` handles LSF
   submission, containers, logging and `-resume`.
3. **Don't run anything compute- or memory-heavy in the terminal.** The login
   node caps memory at ~2 GB. Reading logs, CSVs and small files is fine;
   loading a FASTQ or running an analysis script is not.
4. **Never move, delete, modify or overwrite the raw FASTQs.** They stay where
   the user keeps them: `fastq_r1`/`fastq_r2` (or the `fastq_dir` folder) in
   `config.yaml` point to them, as absolute or project-relative paths. The
   launcher reads them in place and never rewrites those keys. Don't change
   those keys unless the user asks; if the files are moved, update `config.yaml`.
5. **Ask before destructive or expensive actions:** deleting `results/`,
   `metadata/`, `.nextflow/`, or the Nextflow work directory
   (`/project/rephilllab/nf_work/$USER/<this directory's name>/`), or launching
   a run when nothing has changed.
6. **Don't hand-edit files in `results/`** (intermediate files are inside it, in
   `results/intermediate_files/`). They're regenerated by the pipeline; change
   the inputs or an override instead.
7. **Never assume the experiment.** Ask the user for the biological and technical
   context, and flag (never silently resolve) data that contradict it; see the
   next section.

## Ask about the experiment; never assume it

You know the pipeline; only the user knows the experiment. Before you prepare
inputs, choose contrasts, interpret results, or write Methods or figure text,
ask the user for the context below, unless they already gave it in this
conversation or it is in `CONTEXT.md`. Ask even when it seems obvious.

- **The question:** what the screen selects for (proliferation/essentiality,
  drug resistance or sensitivity, a FACS sort on a reporter, survival, ...),
  what a hit would look like (depleted, enriched, or both), and which genes
  they expect to behave how (positive controls, known hits).
- **The screen:** knockout, CRISPRi, CRISPRa, base editing or other; the cell
  line or model; the library (name, version, guides per gene, non-targeting or
  safe-harbour controls); MOI and coverage (cells per guide) at transduction and
  at every passage or sort; the selection (antibiotic, days).
- **Each sample:** what it is (plasmid, pre-selection/day 0, a timepoint, a
  treatment and dose, a sort gate, an unsorted input), which samples are
  biological replicates and which are technical, which samples pair with which,
  and anything that went wrong (low cell numbers, a failed PCR, a contamination,
  a re-sequenced sample).
- **The sequencing library:** how the PCR was done (primers, staggers, inline
  barcodes), single- or paired-end, read length, which run(s) and lanes, whether
  the run also holds other people's samples, and whether the FASTQs are already
  demultiplexed.
- **The comparisons:** which treatment-vs-control comparisons answer their
  question, and in which direction a hit counts.

- Ask in short batches (3-6 questions at a time), in plain language, and say why
  each answer matters. Keep asking until the answers are specific; "the usual"
  or "like last time" is not an answer, so ask what it was.
- **Never infer the design from names** (`D0`, `T14`, `ctrl`, `plasmid`, `R1`,
  `rep2`, `hi`/`lo`) or from what is "typical" for CRISPR screens. Ask what each
  name means.
- Use only what the user confirmed. Where an answer is missing, say what you
  would do instead and wait for an explicit OK; never fill the gap silently,
  and never pick contrasts, controls or replicates yourself.
- **Write the answers down** in `CONTEXT.md` in the project folder (dated, in the
  user's words, with open questions marked as open). Read it at the start of
  every session; ask the user to confirm it is still right before you rely on
  it, and add to it as you learn more. It is tracked by git with the inputs.
- **When the data seem to contradict the context, flag it; don't reinterpret.**
  Examples: a "plasmid" or "day 0" sample with a skewed distribution (high Gini,
  many zero-count guides); a replicate that correlates poorly with its partner;
  essential genes not depleted in a sample described as a late timepoint; a
  sample that maps mostly to another library; a barcode that is never found.
  Show the user the numbers and the file they come from, say what the data
  would be consistent with, and ask. The user's description stands until they
  change it; don't rename samples, drop them or change contrasts on your own.
- Subagents cannot talk to the user: put the confirmed context (or the path to
  `CONTEXT.md`) in every brief, and pass their "Questions for the user" back to
  the user rather than answering them yourself.

## Running

```bash
run_crisprscreen.sh          # from this directory; reads ./config.yaml
```

It's safe to run from the login node: it only checks the FASTQ paths and submits
one LSF head job, then returns. The head job runs every step as its own LSF job,
each in a container.

Re-running is always `run_crisprscreen.sh` again. `-resume` is built in, so any
step whose inputs, script and settings haven't changed is reused from cache.
Only what changed, and anything downstream of it, re-runs. There is no "run
just step X" command: change the thing, re-run, and caching does the rest.

The work directory (and Nextflow's `.nextflow/` cache) is deleted after a successful
run unless `config.yaml` has `keep_work: true` (default `false`); failed or stopped runs
always keep both. So
re-running a finished project recomputes everything (~10-20 min for a full
lane). To reuse the finished steps (e.g. after adding contrasts), `keep_work:
true` must be set before the run.

If `run_crisprscreen.sh` isn't found, the user's `PATH` is missing
`/project/rephilllab/bin`. Tell them, and point them at the "One-time setup"
section of `/project/rephilllab/CRISPR_SCREEN/HPC/README.md`. Don't edit their
`~/.bashrc` without asking.

## Input modes and libraries (read config.yaml to see which applies)

- **`fastq_dir` set:** the samples are already demultiplexed, so
  demultiplexing is skipped and `fastq_r1`/`fastq_r2` are ignored (leave them
  as they are). The FASTQs are read in place from that folder (never moved,
  copied or renamed; `fastq_dir` is not rewritten). Each sample needs
  `<sample_name>.fastq.gz` (or `.fastq`, `_R1`/`_R2` when paired).
- **Only `fastq_r1` set:** the pipeline demultiplexes that multiplexed FASTQ
  using the samplesheet's `barcode` column.
- **Optional `library` column** in `samplesheet.csv`: names each sample's
  library, as the library file's name without `.csv`, among the files matched
  by `library:` (e.g. `libraries/*.csv`). Each library is counted separately
  with only its own samples, and gets its own count table and QC plots.
  Contrasts are tested within the library holding both of their samples.
  Without the column, every sample is counted against every library. Then a
  sample with 0 reads for one library is left out of that library's count
  table (not an error), and
  `results/counts/qc/tables/<project_name>_library_breakdown.csv` / `_wide.csv`
  (also section 0 of the pools comparison report) show what % of each
  sample's reads matched each library, any library, or none — the place to
  check which pool(s) a sample really holds. Each library's `mapping_pct`
  counts only that library's reads, so a low value for a library the sample
  is not in is expected. Contrasts can't be tested in
  this mode (each sample is in every table); add a `library` column first.
- If the user says their samples were screened with different
  libraries/pools, or the QC shows some samples mapping far better than
  others, check whether a `library` column is needed. Ask the user which
  library each sample used; never guess.
- **Guide position (`trim5` in `config.yaml`):** leave unset (the default) —
  the pipeline finds each library's own constant vector sequence
  automatically and positions every guide from it, robust to any plasmid
  design, nothing to configure. Only set `trim5` to a number to force a
  fixed 5' trim length instead (bypasses discovery entirely). If mapping
  looks unexpectedly low, check
  `results/counts/qc/anchor_discovery/<prefix>_anchor_discovery.csv` and
  `<prefix>_anchor_refinement.csv` before assuming `trim5`/`sgrna_len` need
  adjusting — that's the trace of what was discovered, how it was checked
  against the library's guides, and why.

## Monitoring a run

```bash
bjobs -u $USER                                            # LSF jobs; the head job is crisprscreen_<project_name>_<timestamp>
tail -n 50 metadata/nf_logs/nextflow_<timestamp>.out      # latest = ls -t metadata/nf_logs/*.out | head -1
cut -f3-5 metadata/pipeline_info/execution_trace.txt      # per-step status of the latest run (CACHED / COMPLETED / FAILED)
```

A run ends with `Pipeline completed successfully` or `Pipeline FAILED` in the
`.out` log. Poll every few minutes: demultiplexing a full lane takes roughly
10–30 min, and the whole pipeline usually finishes within an hour.

## When a run fails

1. Read the end of the newest `metadata/nf_logs/nextflow_<timestamp>.out`. It
   names the failed step, its exit status, the command, and its `Work dir:`.
2. In that work dir, read `.command.sh` (what ran), `.command.err` and
   `.command.log` (what it said). Most tools also write their own log there.
   For a step that *succeeded*, the same exact command is saved permanently
   next to its results — every `results/.../log/` directory has a
   `<name>_command.sh` alongside the `.log` file, so you don't need the
   work dir (deleted after a successful run, with `.nextflow/`, unless `keep_work: true`) to see
   what ran.
3. Common cases:
   - **Exit status 3** is a known data problem the pipeline detected. It is not
     retried, and the message says what to fix. For example: "these samples
     had 0 reads mapping to the library". That usually means those samples
     belong to a different library or screen: remove them from
     `samplesheet.csv`, or check `sgrna_len` (and `trim5`, only if it's set
     — see "Input modes and libraries" below for the normal, automatic case).
   - **`VALIDATE_CONTRASTS` fails (exit 3):** a `treatment`/`control` pattern
     matched no sample, matched in more than one library, or treatment and
     control sit in different libraries (not comparable). The message lists
     each count table's sample columns. Patterns are regex *searches*, so
     `Pool_1` also matches `Pool_10`; anchor it (`^Pool_1$`) to match one sample.
   - **`GUIDE_ANCHOR_DISCOVERY` fails (exit 3):** only happens when `trim5`
     is unset (the default). Couldn't find a reliable constant sequence
     between this library's barcode and its guide from ~200k reads of its
     first sample. Check `results/counts/qc/anchor_discovery/<prefix>_anchor_discovery.csv`
     for the full trace. Usually means either this library's amplicon
     genuinely has no constant region there, or the sample used for
     discovery isn't what this library's samples should look like. Setting
     `trim5` in `config.yaml` bypasses discovery entirely.
   - **Startup errors** (before any job runs) name the problem directly: a
     sample with no FASTQ in `fastq_dir`, an unknown `library` value, a missing
     `barcode` column when demultiplexing, a script replacement path that
     doesn't exist, or a script path under a key that names no pipeline
     script (a typo; the message lists the valid names).
   - **Exit 137/140/143** (out of memory / wall time): retried automatically,
     with more memory for most steps. Demultiplexing uses a fixed LSF request,
     so its retries don't grow. If a step still fails, report it to the user.
4. Fix the input or config, then re-run `run_crisprscreen.sh`. Completed steps
   are reused.
5. If the failure looks like a bug in the shared pipeline rather than in this
   project's data or config, **tell the user and stop**. Don't patch
   `/project/rephilllab/CRISPR_SCREEN/HPC`.

## Customizing this project's analysis or plots

Every step of the pipeline runs one script from
`/project/rephilllab/CRISPR_SCREEN/HPC/bin/`. To change a step for this project
only, copy that script into `utils/`, edit the copy, and add a `config.yaml`
line **named after the script** (file name without extension) with the
copy's path. The shared script stays untouched for everyone else.

```bash
cp /project/rephilllab/CRISPR_SCREEN/HPC/bin/guide_representation_plot.R utils/   # 1. copy
# 2. edit utils/guide_representation_plot.R
# 3. add to config.yaml:   guide_representation_plot: utils/guide_representation_plot.R
run_crisprscreen.sh                                                           # 4. only that step (+ downstream) re-runs
```

| Script (= `config.yaml` key)                   | What it controls                                                                                                                                  |
| ------------------------------------------------| ---------------------------------------------------------------------------------------------------------------------------------------------------|
| `my_theme.R`                                   | look of every plot (must define a ggplot2 theme named `my_theme`)                                                                                 |
| `guide_representation_report.R`                | the per-library HTML QC report (`results/counts/qc/report/`): assembles the plots below with a description, how to interpret it, and troubleshooting for each |
| `guide_representation_compare_report.R`        | with more than one library: one HTML report comparing every pool side by side (only runs then)                                                   |
| `guide_representation_plot.R`                  | guide-representation QC plots, drawn from `results/counts/qc/tables/`                                                                             |
| `guide_representation_wrangle.R`               | the tables behind those plots (count table → CSVs)                                                                                                |
| `plot_barcode_position.R`                      | barcode-position density plot                                                                                                                     |
| `mageck_count.sh` / `mageck_test.sh`           | the `mageck count` / `mageck test` calls                                                                                                          |
| `library_breakdown.py`                         | with more than one library: % of each sample's reads matching each library (and none)                                                            |
| `demultiplex.sh`, `barcode_position_qc.py`     | demultiplexing and the barcode-position counts (replacing either re-runs demultiplexing, ~30 min)                                                 |
| `cutadapt_stats.py`, `fastqc.sh`, `multiqc.sh` | demux metrics, read QC                                                                                                                            |
| `build_mageck_library.py`                      | library CSV → MAGeCK format                                                                                                                       |
| `discover_anchor.py`, `guide_anchor_trim.sh`   | anchor discovery and trimming through the anchor (only when `trim5` is unset; replacing either re-runs counting)                                 |
| `validate_contrasts.py`                        | contrast validation                                                                                                                               |
| `software_versions.sh`, `write_methods.py`     | tool versions per container, and METHODS.md (the run's Materials and Methods)                                                                    |

- To keep a default script but pass it extra arguments, add
  `<script name>_args: "..."` (e.g. `plot_barcode_position_args: "--bw=1"`,
  `guide_representation_plot_args: "--dpi=150"`,
  `mageck_count_args: "--count-n"`). The `.sh` scripts pass extra
  arguments on to their tool.
- **Plot-only changes** (colors, labels, sizes, adding or dropping a plot):
  replace the **plot** script and/or `my_theme.R`. Plot steps only read
  precomputed tables, so no counting or statistics are redone.
- **Changing what's computed:** replace the matching **wrangle** script. Keep
  its output table names, or also replace the plot script so it reads the
  new ones.
- Each script's header lists the arguments the pipeline passes and the files
  it must write. Keep both compatible. `.py` runs with `python3`, `.R` with
  `Rscript`, anything else with `bash`.
- To try a plot tweak cheaply, re-run the pipeline. Everything upstream is
  cached, so only the plot step runs (usually a minute or two).

Other settings (`trim5`, `sgrna_len`, `paired_end`,
`contrasts`) are documented inline in `config.yaml`. Changing one re-runs the
affected step and everything downstream of it.

## Results

Every step's own `log/` subfolder (shown throughout below) holds both its
`.log` (what the tool said) and a `*_command.sh` (the exact command that
ran, fully filled in — copy-pasteable, and what to send a labmate or agent
when asking for help troubleshooting).

```
results/demultiplexing/log/                 cutadapt log (+ command.sh)
results/demultiplexing/qc/fastqc/           per-sample FastQC
results/demultiplexing/qc/multiqc/          multiqc_report.html — start here for read QC
results/demultiplexing/qc/cutadapt_stats/   per-sample read counts, demux rate, uniformity
results/demultiplexing/qc/demux_plots/      barcode-position density (+ CSV): one sharp shared peak = consistent read structure
results/counts/*.count.txt                  raw sgRNA counts (count_normalized.txt: median-normalized)
results/counts/*.unmapped.txt               reads mageck couldn't match to a guide (mageck count is always
                                             exact-match-only), one column per sample — feeds read classification
results/counts/qc/anchor_discovery/         only when trim5 is unset (the default): the discovered anchor's
                                             full evidence trace, and per-sample anchor-found rates
results/counts/qc/tables/                   every number behind the count QC plots; *_qc_summary.csv = one row per sample, with flags;
                                             with >1 library, <project_name>_library_breakdown*.csv = % of each sample's reads per library
results/counts/qc/plots/                    guide representation, Lorenz/Gini, ECDF, mapping rate (= % exact
                                             match), read classification (exact/near-miss/far-miss), ... SVGs
results/counts/qc/report/                   <prefix>_qc_report.html — one page per library: every plot above with what it
                                             means, how to read it, and what to check if it looks poor. Start here.
                                             With >1 library: also <project_name>_pools_comparison_qc_report.html,
                                             the same plots faceted one panel per pool, for spotting the odd one out.
results/mageck_test/<treatment>_vs_<control>/   gene_summary / sgrna_summary (only if contrasts.csv is set; ^ and $ dropped from the names)
results/METHODS.md                          this outdir's copy of METHODS.md (the project-root copy = latest successful run)
```

`METHODS.md` (project root, and a copy in the outdir) is the Materials and Methods of the
last successful run: only the steps it performed, with the parameters and versions they
actually used, read from the tools' own logs and `metadata/pipeline_info/run_info.json`.
Hand it to the user when they ask how the analysis was done or for a methods section. It is
regenerated by every successful run, so don't edit it in place: copy it before adapting it.
Text marked **[To complete: …]** needs the user's input (e.g. how already-demultiplexed reads
were demultiplexed, or what a replaced script does).

When summarizing results, start from `results/counts/qc/report/<prefix>_qc_report.html` (or
`*_qc_summary.csv` directly — `library_skew_flag`, `undetected_flag`, `mapping_pct`) and the
MultiQC report. In an all-vs-all run (more than one library CSV, no `library` column), a low
`mapping_pct` for one library is expected for samples of other libraries; in
`_library_breakdown_wide.csv` (which library a sample belongs to), Low mapping means
`pct_any_library` < 30 and a "Mainly <library>" badge is neutral. Otherwise Low mapping means
`mapping_pct` < 30, usually a sample from a different library, or `trim5`/`sgrna_len` don't match
its read structure. The Read
Classification plot tells you which: mostly **near-miss** (1 base off a real guide) points to
`trim5`/`sgrna_len` or sequencing quality; mostly **far-miss** (not close to any guide) points
to a wrong/different library.

| Papers and citations | `literature-scout` | sonnet |
| How MAGeCK or the pipeline code works | `code-researcher` | sonnet |

Rules for every subagent:

- Read-only in the pipeline folder `/project/rephilllab/CRISPR_SCREEN/HPC`; never edit `original_data/`.
- Never start, stop or clean a run: only the lead does that, with `run_crisprscreen.sh`. The Hard rules
  apply to subagents too (no `nextflow`, `mageck`, `cutadapt`, `Rscript`, analysis scripts, `bsub`).
