# AGENTS.md — CUT&RUN / chromatin profiling project (Richard Phillips Lab), Docker version for Mac

This folder is **one lab member's CUT&RUN / CUT&Tag project**, run with the
lab's shared pipeline (Docker version for Mac) installed on this computer at:

    {{PIPELINE_DIR}}

You are here to help this user run the pipeline on *their* data, check results,
and customize *their* analysis. The user is usually a wet-lab scientist: do the
technical work, explain in plain language, and ask them for what only they know.
You are not here to change the pipeline itself.

## Hard rules

1. **Never edit anything in the pipeline folder above** (or anywhere in its git
   clone) unless the user explicitly asks to change the **lab-wide** pipeline.
   To change how this project's analysis or plots work, use a per-project
   override (see "Customizing").
2. **Only launch the pipeline with this project's `utils/run_cutandrun.sh run`,
   and run this project's own analysis scripts with its `script` command** (see
   "Analyses beyond the pipeline"). Don't call `docker run`, `nextflow`,
   `bowtie2`, `samtools`, `Rscript`, `python`, or the pipeline's `bin/` scripts
   yourself. The launcher handles Docker, the input checks, logging and resuming.
   Never call `RUN_ANALYSIS.command` (it's the double-click launcher for humans and
   waits for a key press).
3. **Don't run analysis work on the computer itself.** Reading logs, CSVs and
   other small text files is fine. Opening FASTQ or BAM files, or running any
   analysis, is not: that goes through `script` (or `run`), where the pipeline's
   image and memory limits apply.
4. **The raw FASTQs and BAMs are the user's data.** They stay where the user keeps
   them: the paths in `config.yaml` and `samplesheet.csv` point to them, and the
   launcher reads them in place, read-only. Never move, copy, rename, delete or
   overwrite them. `fastq_dir` is not used by this version: leave it `null`.
5. **Ask before destructive or expensive actions:** deleting `results/`,
   `intermediate_files/` or `metadata/`; `clean` (it deletes `metadata/work/` and
   `metadata/.nextflow/`); changing `keep_work`; or launching a run when nothing
   has changed. A full run takes hours and a lot of disk.
6. **Don't hand-edit files in `results/` or `intermediate_files/`.** They are
   regenerated by the pipeline; change the inputs or an override instead.
7. **Don't guess data paths.** FASTQ, BAM, genome index, blacklist, GTF and TSS
   paths come from the user. Ask.
8. **Never assume the experiment.** Ask the user for the biological and technical
   context, and flag (never silently resolve) data that contradict it; see the
   next section. Record the answers in `CONTEXT.md`.
9. **The computer's settings are the user's.** Don't change Docker Desktop's settings
   (its Memory limit included), and don't install software (Docker Desktop, Homebrew
   packages, Rosetta, or anything inside the container at run time) without asking. When
   the launcher asks a question about an install or about Docker's memory, answer only
   with the user's OK; don't add `--yes` on your own.

## Ask about the experiment; never assume it

You know the pipeline; only the user knows the experiment. Before you prepare
inputs, choose peak sets or comparisons, interpret results, or write Methods or
figure text, ask the user for the context below, unless they already gave it in
this conversation or it is in `CONTEXT.md`. Ask even when it seems obvious.

- **The assay:** CUT&RUN or CUT&Tag, and the kit or protocol (this decides
  `experiment` in `config.yaml`: `cutandrun` or `cutandtag`). The cell line or model.
- **The antibodies:** for each antibody, the protein or mark it targets, and what a
  good profile should look like (broad or narrow peaks, where, how strong).
- **Each sample:** the treatment, dose and timepoint; which libraries are
  biological replicates and which are technical; which IgG control pairs with
  which library (`control_id`); whether a spike-in is present, and whether it is
  E. coli carry-over or was added on purpose; and anything that went wrong (low
  input, a failed library, a re-sequenced sample).
- **The sequencing:** paired-end or single-end, the read length, which run(s) and
  lanes, and whether the FASTQs are already demultiplexed. This pipeline version
  supports paired-end data only (`paired_end: true`); say so if the data are
  single-end.
- **The comparisons:** which treatment-vs-control comparisons answer their question
  (which groups are the reference and which the treated, and whether the retained
  or lost classes matter), and the expected positive and negative loci (genes or
  regions that should or should not bind or change).

- Ask in short batches (3-6 questions at a time), in plain language, and say why
  each answer matters. Keep asking until the answers are specific; "the usual"
  or "like last time" is not an answer, so ask what it was.
- **Never infer the design from names** (`rep2`, `A`/`B`, `ctrl`, `T0`, `T14`,
  `DMSO`, `hi`/`lo`) or from what is "typical" for CUT&RUN or CUT&Tag. Ask what
  each name means.
- Use only what the user confirmed. Where an answer is missing, say what you
  would do instead and wait for an explicit OK; never fill the gap silently,
  and never pick controls, replicates or comparisons yourself.
- **Write the answers down** in `CONTEXT.md` in the project folder (dated, in the
  user's words, with open questions marked as open). Read it at the start of
  every session; ask the user to confirm it is still right before you rely on
  it, and add to it as you learn more. It is tracked by git with the inputs.
- **When the data seem to contradict the context, flag it; don't reinterpret.**
  Examples: an IgG library with a high FRiP (`results/qc/frip/`); a replicate
  that correlates poorly with its partner (`results/qc/correlation/`); a "global
  loss" treatment where the ChIPseqSpikeInFree factors do not move
  (`results/scale_factors/`); a mark expected to be broad giving narrow peaks.
  Show the user the numbers and the file they come from, say what the data would
  be consistent with, and ask. The user's description stands until they change
  it; don't rename samples, drop them or change comparisons on your own.
- Subagents cannot talk to the user: put the confirmed context (or the path to
  `CONTEXT.md`) in every brief, and pass their "Questions for the user" back to
  the user rather than answering them yourself.

If git is installed, this folder is a git repository tracking `config.yaml`,
the input CSVs, `examples/` and any override scripts. Data, results and logs
are gitignored. Committing after a meaningful config change is a good habit,
but ask the user first.

## Running

From this folder:

```bash
bash utils/run_cutandrun.sh run --detach    # start (or resume) the analysis; returns immediately
bash utils/run_cutandrun.sh status          # running / succeeded / failed + step counts + last log lines
bash utils/run_cutandrun.sh logs            # follow the live log (Ctrl+C stops watching; the run goes on)
bash utils/run_cutandrun.sh stop            # stop; the next run resumes
bash utils/run_cutandrun.sh clean           # delete metadata/work and the resume cache (asks first)
```

A different config file: `run --detach other.yaml`.

The analysis runs inside Docker Desktop, in the background: closing the
terminal doesn't stop it, but the Mac must stay on, plugged in, lid open (the launcher
prevents idle sleep while the run is active). Docker Desktop must be running; the launcher
starts it if needed (it can take a minute or two).

Re-running is always `bash utils/run_cutandrun.sh run` again. Resuming is built in,
so any step whose inputs, script and settings haven't changed is reused. Only
what changed, and anything downstream of it, re-runs. There is no "run just step
X" command: change the thing, re-run, and caching does the rest.

Nextflow's work folder is `metadata/work/` and its resume cache is
`metadata/.nextflow/`. `keep_work` in `config.yaml` defaults to `true`: they are
kept, so a re-run resumes and only redoes what changed. With `keep_work: false`
they are deleted after a successful run, and re-running then recomputes
everything. Failed or stopped runs always keep them. `publish_mode` defaults to
`auto`: files in `results/` and `intermediate_files/` are hard links to the files
in `metadata/work/` when the disk allows, so big files are not stored twice.
Never edit a published file in place (replacing or deleting is fine). An explicit
`publish_mode` in `config.yaml` wins (the template sets `copy`).

First time on a Mac: Docker Desktop and the pipeline's software image are a
one-time setup. Ask the user first, then run
`bash "{{PIPELINE_DIR}}/run_cutandrun.sh" setup --yes` (it installs Docker Desktop with
Homebrew if Homebrew is present, after asking; without Homebrew it prints the download
page; it installs Rosetta 2 on Apple chips, after asking; it downloads the image; a
restart may be needed). `setup` also prints the versions of the image's tools (see "Key
config choices"). Then, in a new project:
`bash "{{PIPELINE_DIR}}/run_cutandrun.sh" init "<folder>"`. `init` creates the
folder layout, fetches the templates, these agent files and the `.claude/agents/`
kit (when the pipeline has them), writes `.gitattributes`, sets up git if it is
installed, and rewrites the two launchers. It never overwrites `config.yaml`, the
CSVs or the agent files.

If `utils/run_cutandrun.sh` here fails with "No such file or directory", the pipeline
folder moved: re-run `bash "<new pipeline folder>/run_cutandrun.sh" init "<this folder>"`.

## Input files

### samplesheet.csv: one row per library

```
sample_id,fastq_1,fastq_2,bam,antibody,condition,replicate,control_id,group,norm_run,exclude
```

| Column | Meaning |
|---|---|
| `sample_id` | Unique library name. Used verbatim in file names; must match `^[A-Za-z0-9][A-Za-z0-9_.-]*$`. |
| `fastq_1`, `fastq_2` | Paths of the R1 / R2 FASTQ (paired-end only), e.g. `/Users/you/data/K27me3_A_R1.fastq.gz`. Fill these OR `bam`, never both. |
| `bam` | A pre-aligned, final-filtered BAM (leave `fastq_1/fastq_2` empty). Skips trim, align and filter; it is linked in as `<sample_id>.final.bam`. Such a row has no raw stats and no spike-in BAM, so it is not usable for spike-in normalisation. |
| `antibody` | Normalised antibody/mark name (`IgG`, `K27me3`, `K27me2`, `CBX2`, ...). `IgG` (any case) marks a control library. |
| `condition` | Treatment/genotype label (`DMSO`, `K27MKO_EZH2i`, ...). |
| `replicate` | Replicate label (`1`, `2` or `A`, `B`). |
| `control_id` | `sample_id` of this library's IgG control (a control is any row whose `antibody` is `IgG`, case-insensitive). Must be empty for the IgG rows themselves. Startup fails if it names a missing, excluded or non-IgG sample. Needed for MACS3, SEACR and log2-ratio bigWigs. MACS3 and SEACR are on by default: without a `control_id` for every target they are skipped with a warning, unless `run_macs3` / `run_seacr` were set to `true` explicitly or `run_log2ratio` is on (startup error); csaw is not affected. |
| `group` | The unit of replication for csaw, fingerprint and consensus peaks; must match `^[A-Za-z0-9][A-Za-z0-9_.-]*$`. If empty it defaults to `<condition>_<antibody>` (startup error if that cannot be derived). `peaksets.csv` refers to these values. |
| `norm_run` | Which `norm_runs.csv` row normalises this library. Required for every non-skipped row unless `normalisation: cpm`; must exist in `norm_runs.csv`. May be empty for rows in `skip_groups`. |
| `exclude` | empty/`false`/`0`/`no` keep the row; `true`/`1`/`yes` drop it from the whole run (anything else is a startup error). |

Rules enforced at startup (the run stops with a message before any step starts):
required columns present, unique `sample_id`, every `control_id` exists and is a
control, every `norm_run` exists in `norm_runs.csv`, every file exists, exactly
one of (`fastq_1`+`fastq_2`) or `bam` per row.

**`skip_groups`** (config key, default none): a comma list of
`group` values. Rows in those groups stay in the samplesheet but are skipped by
every core step (QC, normalisation, bigWigs, peaks).

### norm_runs.csv: one row per normalisation run

```
norm_run,method,bin_size,cutoff,max_turns[,min_first_turn][,ref_condition]
```

- `norm_run`: name referenced by the samplesheet.
- `method`: the run's PRIMARY method: `chipseqspikeinfree`, `spikein`, `tmm` or `cpm` (library size only, numbers blank). Only the primary scales the bigWigs and the classification; see "Normalisation methods" below.
- `bin_size`, `cutoff`, `max_turns`: parameters of ChIPseqSpikeInFree; all
  three must be numeric for `chipseqspikeinfree` rows. Blank for `spikein`
  rows. For `tmm` rows `bin_size` may be blank (then `tmm_bin_size` from
  `config.yaml` is used). A `spikein` run cannot contain pre-aligned `bam` rows
  (no spike-in reads): startup error.
- `min_first_turn` (optional, `chipseqspikeinfree` only): numeric; blank = 0.5, the package default. Passed to the script as `--min-first-turn=` and recorded in the scale-factor `note`.
- `ref_condition` (optional): reference condition of the run's MA plots; blank = the condition of the `ref_group` of the classifications that use the run (if exactly one), else the condition of the run's first library. Must be a condition of the run.
- Each run's samples are normalised together; IgG usually has its own run.
  Output: `results/scale_factors/<norm_run>.scale_factors.tsv`.

### peaksets.csv: one row per csaw peak set

```
peakset,target_group,control_group,small_filt,large_filt,merge_bp,max_width,fdr,lfc
```

- `peakset`: output name (`results/peaks/csaw/<peakset>.peaks.bed`, ...).
- `target_group`, `control_group`: `group` values from the samplesheet (target
  versus IgG); each must be a group of at least one active (non-excluded,
  non-skipped) sample, else startup error.
- `small_filt`, `large_filt`: csaw filter thresholds on the small-window and
  large-bin log2 enrichment over background; `merge_bp`: max gap when merging
  windows; `max_width`: max merged region width (blank = no limit, passed as 0);
  `fdr`, `lfc`: region-level FDR and log2 fold-change cutoffs.
- A blank threshold cell takes `csaw_defaults[<antibody of target_group>]`, else the global
  `csaw_<column>` (`csaw_small_filt`, ..., `csaw_lfc`). Startup fails if a target group mixes
  antibodies or a resolved value is not numeric. `metadata/peaksets.resolved.tsv` shows each
  resolved value and its source (`row`, `antibody` or `global`).
- Header-only is valid, with `run_csaw: false`.

### classifications.csv: one row per region classification (used when `run_classify: true`)

```
classification,regions,ref_group,treat_group,norm_run,lfc_retained,lfc_lost,fdr
```

- `classification`: id (`^[A-Za-z0-9][A-Za-z0-9_.-]*$`, unique); prefix of the outputs and of the
  region names `<id>.retained`, `<id>.lost`, `<id>.unclassified`, which heatmaps, tracks and
  intersects accept wherever a region or BED name is accepted.
- `regions`: a csaw peak set name (needs `run_csaw`) or the path of a BED file.
- `ref_group`, `treat_group`: samplesheet `group` values (reference, treated). They must differ,
  and each needs at least one active sample.
- `norm_run`: empty = the `norm_run` shared by all those samples (startup error if they differ or
  a sample has none). Otherwise a `norm_runs.csv` row. Scale factors are read from its
  `edger_norm_factor` column only.
- `lfc_retained`, `lfc_lost`, `fdr`: empty = `classify_lfc_retained` (-1), `classify_lfc_lost` (-2),
  `classify_fdr` (0.05).
- Classes: lost = logFC <= lfc_lost and FDR < fdr; retained = round(logFC, 1) >= lfc_retained or
  FDR >= fdr; unclassified = the rest; a region that is both lost and retained is lost.
- Outputs in `results/classify/<id>/`: `<id>.{retained,lost,unclassified}.bed` (BED6, 0-based starts),
  `<id>.per_region.tsv.gz`, `<id>.summary.tsv`, `<id>.ma.svg`.

### heatmaps.csv: one row per heatmap (used when `run_heatmaps: true`)

```
heatmap,regions,samples,labels,window_bp,bin_bp,sort_using,cluster_k,z_min,z_max,y_max,colors,engine,cluster_samples,cluster_labels,legend_title,region_labels
```

- `heatmap`: id; used in every output name.
- `regions`: a csaw peak set name, a class name (`<id>.retained`, ...), an intersect name (its `.intersect.bed`), or the path of an existing
  BED file. A quoted list gives one region group per entry (`region_labels`, optional, one label
  per entry). `enrichedheatmap` and any row with `cluster_k` accept one region only.
- `samples`, `labels`, `colors`: quoted comma lists, one entry per sample. A literal
  `\n` in a label gives a line break. `colors`: one hue per sample (`"#8c96c6"`),
  ramped from white.
- `window_bp`, `bin_bp`: bp on each side of the region centre, and the bin size.
  `window_bp` must be a multiple of `bin_bp`.
- `sort_using`: empty, or one `sample_id` whose signal sorts the rows.
- `cluster_k`: empty or `0` = no clustering; an integer >= 2 = that many clusters;
  a range such as `2-6` = the gap statistic chooses k.
- `z_min`, `z_max`, `y_max`: empty, one number, or one per sample. `y_max` (profile
  height) is independent of `z_max` (colour scale). `z_max` and `y_max` may be `auto` (deepTools
  engine only): HEATMAP_LIMITS sets each sample's limit to round_up_2sf(1.05 x the largest mean
  profile maximum of its antibody's samples), table `results/heatmaps/limits/<heatmap>_limits.tsv`.
- `engine`: `deeptools` or `enrichedheatmap`.
- Optional: `cluster_samples` (subset of `samples` used for clustering; empty = all),
  `cluster_labels` (quoted, k entries; otherwise `cluster 1` .. `cluster k`),
  `legend_title` (EnrichedHeatmap legend; empty = the sample's antibody).
- Clustering is a separate seeded step (`heatmap_cluster.py`, KMeans with
  `random_state = heatmap_seed`). Do not use `plotHeatmap --kmeans`: it is unseeded.
  Cluster BEDs are written to `results/heatmaps/cluster/`.

### tracks.csv: one row per track set (used when `run_tracks: true`)

```
track_set,locus_or_gene,flank,samples,labels,colors,max_value,beds,scalebar,log2ratio,bed_colors,bed_labels
```

- `track_set`: id; one figure per locus, `results/tracks/plots/<track_set>.<locus>.svg`.
- `locus_or_gene`: quoted comma list of gene names (exact `gene_name` in the GTF) and/or
  regions `chr:start-end`. An unknown gene is an error.
- `flank`: bp on each side of a gene; one value or one per locus; ignored for regions.
- `samples`, `labels`, `colors`: as in heatmaps (one entry per sample).
- `max_value`: one entry per sample: a number, `auto` (autoscale), `group:NAME` (the shared limit of
  the tracks with that name at the locus), or blank = `tracks_max_value_default` (`shared`: one group
  per samplesheet antibody). Set `tracks_max_value_default: auto` for per-track autoscale. `tracks_limit_stat` chooses the statistic of the shared limit: `mean_bins` (default) or `max_bin` (CBX2 rule); `<slug>_limits.tsv` records it (`stat`, `track_peak`).
  TRACKS_LIMITS writes `results/tracks/limits/<slug>.resolved.ini` and `<slug>_limits.tsv`.
- `beds`: quoted list of csaw peak set names, class names (`<id>.retained`, ...), intersect names or BED paths, drawn
  as BED tracks. `bed_colors` (optional, one hex colour per entry, default `track_bed_color`) and
  `bed_labels` (optional, one title per entry, default the file name without extension).
- `scalebar`: bp; empty = no scale bar.
- `log2ratio` (optional): `true` or `false`. Adds the `S.vs_<control_id>.log2ratio.bw`
  track after each sample's bigWig; those files exist only with `run_log2ratio: true`.

### intersects.csv: one row per intersection (used when `run_intersect: true`)

```
name,bed_a,bed_b,label_a,label_b,min_overlap,reciprocal[,output]
```

- `name`: output prefix: `results/intersect/<name>.intersect.bed`, `<name>.only_a.bed`,
  `<name>.intersect_summary.tsv`.
- `bed_a`, `bed_b`: peak set names, class names (`<id>.retained`, ...) or BED paths (intersect names are not accepted here). The output keeps the records of `bed_a`
  that overlap `bed_b`, each once (`bedtools intersect -wa -u`).
- `label_a`, `label_b`: labels in the summary table.
- `min_overlap`: fraction 0-1 of `bed_a` that must overlap; empty = the script default (0.05).
- `reciprocal`: `true` also requires the same fraction of `bed_b`.
- `output`: `records` (default, also when empty) writes each `bed_a` record that overlaps `bed_b` once; `overlap` writes the overlapping pieces, one line per `bed_a`/`bed_b` pair (`bedtools intersect` without `-wa -u`), as the legacy step_7b script and the GG_CBX2 paper heatmaps used. Counts in the summary stay record-based; `n_pieces` counts the lines of `<name>.intersect.bed`.

### Input paths on a Mac

- Write paths in full (`/Users/you/data/x.fastq.gz`, `/Volumes/LabNAS/data/x.fastq.gz`), with
  `~/` (`~/data/x.fastq.gz`), or relative to this folder (`original_data/x.fastq.gz`).
- A file on a drive is read in place. The top-level folder holding it (`/Users`,
  `/Volumes/<name>`, or e.g. `/data`) is mounted **read-only** inside the analysis at the same
  path. Nothing is copied from it. The drive must be connected when the run starts, or the
  launcher stops before anything runs.
- Docker Desktop shares only `/Users`, `/Volumes`, `/private`, `/tmp` and `/var/folders` by
  default. For a folder elsewhere, add it in Docker Desktop → Settings → Resources → File
  sharing (the launcher stops with that message until you do; or move the file under `/Users`
  or `/Volumes`).
- **Network paths (`smb://...`, `cifs://`, `afp://`, `nfs://`, `//server/share/...`) are
  refused.** Mount the share in Finder (it then appears under `/Volumes/<name>`) and write the
  `/Volumes/<name>/...` path.
- No path may contain a comma (it breaks the container's mount).
- The output folders `outdir`, `metadata_dir` and `intermediate_dir` must be relative
  (`./results`, `./metadata`, `./intermediate_files`); an absolute path there is refused.
- Only `config.yaml` and the CSV files in the project folder itself are checked and
  mounted. Keep the working CSVs there (the samplesheet must be there), and use
  `examples/` for templates.
- Paths are used exactly as written: no translation happens on a Mac, so no
  `metadata/host_paths.tsv` is written.
- Reference files on the lab's Windows PC are in `D:\REFERENCES`. That is an **example layout**,
  not a requirement; on this Mac, ask the user where their files are. For example:

```yaml
genome_index: /Users/<you>/REFERENCES/bowtie2/t2t_ecoli/t2t_ecoli   # bowtie2 index PREFIX (T2T-CHM13 + E. coli spike-in)
chrom_sizes: /Users/<you>/REFERENCES/chr_size/t2t_ecoli.chrom.sizes
blacklist: /Users/<you>/REFERENCES/blacklist/t2t.blacklist.cut.and.run.bed
gtf: /Users/<you>/REFERENCES/genomes/t2t/t2t.ncbiRefSeq.curated.norandom.gtf
tss_bed: /Users/<you>/REFERENCES/genomes/t2t/t2t.curated.norandom.tss.bed
```

## Example projects

`examples/projects/{nucleation,cbx2,eed}/` each hold a complete `config.yaml`,
`samplesheet.csv`, `norm_runs.csv`, `peaksets.csv` and a
README listing the values that were inferred rather than copied. They re-create the three
manuscript analyses (nucleation: ChIPseqSpikeInFree, 16 CUT&RUN libraries; cbx2: E. coli spike-in normalisation, 32
libraries, `bigwig_bin_size: 50`; eed: ChIPseqSpikeInFree, 35 libraries, csaw peak sets and
classifications for K27me3 and K27me2). Their paths are the legacy Linux paths
(`/path/to/mylibrary/...`) of the lab's earlier projects: copy the folder's files
to a new project, rewrite every path as a Mac path (see "Input paths on a Mac"),
confirm the reference files with the user, and adapt them. Never run an example in place.

## Key config choices (config.yaml; every key has a default)

- **bowtie2 (alignment):** run as `--local --very-sensitive-local -q --no-mixed
  --no-discordant --dovetail` (`bowtie2_mode: local`, the default; `end_to_end` gives
  `--end-to-end --very-sensitive`). `-I` and `-X` are added only when set:
  `bowtie2_minins` and `bowtie2_maxins` `null` = omitted, so bowtie2's defaults apply
  (-I 0, -X 500), as in the manuscript. 700 for `bowtie2_maxins` and 10 for
  `bowtie2_minins` were 2026-10 test values. Changing either re-runs alignment and
  everything downstream. `csaw_max_frag` (`null` = `bowtie2_maxins`, else 500; also the `max.frag` of the bin counts behind NORM_QC, TMM and the replicate metrics) follows it.
- `mapq: 30`, `trim_minlen: 25`, `trim: true`: trimming and mapping-quality settings.
- `experiment`: `cutandrun` (TruSeq3-PE-2 adapters) or `cutandtag` (NexteraPE-PE).
- **Duplicates:** target AND spike-in reads are deduplicated by default
  (`remove_duplicates: true`, `spikein_dedup: true`; IgG is always
  deduplicated). Setting either to `false` changes every normalisation factor.
- **Normalisation is per project, per `norm_run`:** the samplesheet `norm_run` decides.
  NUC and EED use `chipseqspikeinfree`, CBX2 uses the E. coli `spikein`. The
  `normalisation` key is informational. `cpm` means no scale-factor tables and bigWig
  multiplier 1.
- **Normalisation methods (2026-10-27).** `method` in `norm_runs.csv` is the run's **primary** method and the only one that scales the bigWigs and the classification (`cpm` is allowed too: library size only; a run with one library needs it). Every run with at least two libraries also computes the methods of `norm_methods` (default `chipseqspikeinfree,tmm,cpm`; `''` = primary only) as diagnostics, and physical spike-in when `norm_spikein: true` (a run with pre-aligned BAMs: `unavailable`, with a warning). They are in `results/scale_factors/<norm_run>.scale_factors_all.tsv` and `results/scale_factors/methods/`; `<norm_run>.scale_factors.tsv` is the primary alone and unchanged. ChIPseqSpikeInFree as a diagnostic takes blank CSV cells from `csif_bin_size` 10000, `csif_cutoff` 1.2, `csif_max_turns` 0.99. Choose the primary with the user before the results are seen and record it in `CONTEXT.md`; do not switch it because another method looks better in the MA plots.
- **Normalisation QC and replicate concordance.** `results/norm_qc/<norm_run>.ma.svg` (+ `.ma.p2.svg`, ...; `norm_qc_panels_per_page` 12) has one MA panel per replicate pair and per treated-vs-reference pair (reference = `ref_condition` of `norm_runs.csv`, else the condition of the `ref_group` of the classifications that use the run, else the first library's); y = log2 CPM of `other` minus `ref` (negative = less signal); the dashed line of each method is where it declares "no change" (log2 of the ratio of the `edger_norm_factor`s, 0 for CPM; dotted = factor from a QC-failed or imputed library); settings `norm_qc_min_count` 20 and `norm_qc_prior` 0.5. A line on the cloud is automatic for TMM and CPM and is not evidence that they are right when the treatment changes the mark globally; between replicates every reliable method should lie on the cloud. `results/qc/replicate_correlation/replicate_correlation.tsv` gives per replicate pair Pearson (log2 CPM, `repcor_prior` 2) and Spearman correlation over `repcor_bin_size` bins (null = `tmm_bin_size`), the same on the top `repcor_signal_frac` 0.10 of bins, the robust spread of the log2 ratio, and the median correlation with the other groups of the same antibody (context). These are descriptive, with no pass/fail thresholds. `run_replicate_correlation` and `run_deeptools_correlation` (the all-sample Spearman heatmap) are both on by default.
- `bigwig_units` (`rpkm`|`cpm`|`none`) and `bigwig_bin_size` (10 in the template; 50 in the
  nucleation example) apply to targets and IgG alike. `bigwig_extend_reads: true` draws
  fragments, not reads.
- `csaw_norm_bins`: `background` (default) or `all`.
- csaw knobs (defaults keep the current behaviour): `csaw_large_window` 2000, `csaw_large_spacing` 500,
  `csaw_bg_max_enrich` 1, `csaw_count_filter` 10, `csaw_max_frag` (see above),
  `csaw_lfc_from` (`combined` = legacy rule and the pipeline's rule before 2026-10-23; `best` = best-window logFC),
  `csaw_disjoint_regions` (`false`). Global fallbacks for blank `peaksets.csv` cells: `csaw_small_filt` 3,
  `csaw_large_filt` 1.5, `csaw_merge_bp` 50, `csaw_max_width` 0, `csaw_fdr` 0.05, `csaw_lfc` 1; per-antibody
  map `csaw_defaults` (keys = samplesheet antibody of the target group).
- Region classification, off by default: `run_classify` (CSV `classifications`); blank cells take
  `classify_lfc_retained` -1, `classify_lfc_lost` -2, `classify_fdr` 0.05.
- Peak callers: `run_csaw`, `run_macs3` and `run_seacr` are all on by default. MACS3 and SEACR need an IgG `control_id` per target: without one they are skipped with a warning, unless `run_macs3` / `run_seacr` were set to `true` explicitly (then a missing control is a startup error). Broad or narrow is decided per group from its antibody against `broad_marks` (default `H3K27me3, H3K27me2, H3K36me3, H3K4me1, H3K79me2, H3K79me3, H3K9me1, H3K9me2, H3K9me3, H4K20me1, H3F3A`: the ENCODE histone ChIP-seq broad list plus H3K27me2 by lab request and H3K9me3, an ENCODE "exception" treated as broad by St. Jude; case-insensitive, histone prefix optional: `K27me3` = `H3K27me3`). `macs3_broad` `auto` | `true` | `false` (default `auto`): broad uses `--broad --broad-cutoff` `macs3_broad_cutoff` (0.1), narrow gives narrowPeak with `-q` `macs3_qvalue`. `seacr_mode` `auto` | `relaxed` | `stringent` (default `auto` = relaxed for broad marks, stringent otherwise); lab policy: SEACR has no broad mode (relaxed = threshold between the knee and the peak of the total-signal curve, stringent = the peak). Groups mixing broad and narrow antibodies are a startup error. The mode per group is logged and written to `metadata/peak_call_modes.tsv`; tell the user which mode each group got. Other optional steps: `run_log2ratio`, `run_csaw_cutoff_scan` (a post-hoc diagnostic that never feeds thresholds); `run_csaw` and `run_report` are on.
- Stage 2, all off by default: `run_heatmaps` (CSV `heatmaps`), `run_tracks` (CSV
  `tracks`), `run_annotation`, `run_intersect` (CSV `intersects`). Annotation labels

  `tracks_width` (15 cm) and `tracks_dpi` (600); `heatmap_seed` (42) seeds the clustering.
  Heatmap styling `heatmap_*` (deepTools engine only; `heatmap_reference_point` `center`,
  `heatmap_plot_type` `se`, `heatmap_height` 12, ...) and track styling `track_*` (`track_number_of_bins` 700,
  `track_bed_color` `'#8c96c6'`, `track_log2_min` -6, `track_log2_max` 2, ...); `tracks_max_value_default`
  (`shared`); `tracks_limit_stat` (`mean_bins`). The parameter table in `{{PIPELINE_DIR}}/../HPC/README.md` lists every default.

## Peak QC tracks (new)

New in this version, and on by default: `run_peak_qc: true` runs the step `PEAK_QC_REGIONS`
(`bin/peak_qc_regions.py`) whenever a peak caller (csaw, MACS3 or SEACR) makes peaks. It picks
a short list of regions per mark (the marker loci you ask for, plus optionally a negative
locus) from the peak sets, the region classes and the bigWigs, and draws them as the track set
`peak_qc` in `results/tracks/peak_qc/` (the figures also need `run_tracks: true`). Its settings
are in `nextflow.config`, which holds the current names and defaults:

- `run_peak_qc`: master switch.
- `peak_qc_loci`: `[NAME=]SPEC[:FLANK],...` (gene, glob, `chr:start-end`); empty = default marker loci for Polycomb marks. Ask the user which loci they want; never guess marker genes.
- `peak_qc_negative`: `auto`, `none` or `GENE[:FLANK]` (or `chr:start-end`).
- `peak_qc_max_regions`: cap on automatic regions (user loci are never dropped).
- `peak_qc_exclude_bed`: passed only when set explicitly; the blacklist is always used.
- `peak_qc_nopeak_igg_max_fold`: default 1.5; the peak-free high-signal tile excludes tiles whose IgG signal fold is above it (`null` or `''` = off); only applies when an IgG bigWig exists. The peak sets of every caller are drawn as tracks labelled `csaw <set>`, `MACS3 <group>`, `SEACR <group>` (black, #0072B2, #D55E00).
- `peak_qc_shape_marks`: marks that get the largest, median and densest regions (at most 3).

Its signal criteria are untested on real bigWigs: review `regions.detail.tsv`
(the folds it reports) before trusting the regions it picks. Its files (`regions.tsv`,
`tracks.loci.txt`, `regions.detail.tsv`, `params.json`, `peak_qc_regions.log`) are in
`results/tracks/peak_qc/`; the regions are a suggestion to check, not a result.

## Memory and Docker Desktop's memory (this Mac)

- **Run budget.** The most one analysis may use is the smallest of: 75% of the
  Mac's memory (always leaving 3 GB to macOS), what Docker Desktop may use (its Memory
  setting, minus about 0.5 GB for its own system), and 14 GB (the most the
  pipeline can put to use). CPU cores: all but one or two. `max_memory_gb` and
  `max_cpus` in `config.yaml` lower the budget (they cannot go above Docker's limit).
  The run log banner states the budget and why. The budget must be at least about
  5 GB (`docker/requirements.conf`, `min_memory_gb`); below that the run refuses to
  start, with a plain message. Both figures in `docker/requirements.conf` are
  placeholders until a pilot run on a real Mac.
- **Docker Desktop's memory (recommended, never changed by the launcher).** Docker Desktop's
  Memory setting (Settings → Resources) limits the VM the analysis runs in. For analyses the
  launcher recommends, by the Mac's RAM: under 12 GB, 6 GB; 12 to under 24 GB, 8 GB; 24 GB or
  more, 16 GB. The user sets it (Apply & restart) if they agree; ask first. When Docker's
  setting holds the budget back, the run's note says so and gives the setting to change. The
  launcher never edits Docker Desktop's settings.
- On smaller tiers the heavy steps get fewer cores and a smaller share of memory
  (`conf/docker_tiers.config`); the figures are estimates until the pilot runs are done.
- A step killed for running out of memory (exit 137) is retried with more memory,
  within the budget (see "When a run fails").

## Monitoring a run

```bash
bash utils/run_cutandrun.sh status                                       # the summary; use this
tail -n 50 "$(ls -1 metadata/nf_logs/nextflow_*.log | sort | tail -1)"   # the newest Nextflow log
head -40 metadata/pipeline_info/execution_trace.txt                      # one row per step (tab-separated)
```

`status` says `RUNNING`, or `last run succeeded`, `last run failed (exit N)`,
`last run interrupted` (Docker or the Mac stopped mid-run: just run again) or
`last run stopped by the user`. A finished run is also written in
`metadata/nf_logs/last_run.status` (`succeeded` or `failed (exit N)`).
Poll every few minutes: alignment of a full project takes hours on a laptop.

## When a run fails

1. `bash utils/run_cutandrun.sh status` names the failed step and its exit status,
   and the folder `metadata/failed_tasks/<timestamp>/` with the failed step's files.
2. Read `metadata/failed_tasks/<timestamp>/<step>/`: `command.sh` (what ran),
   `command.err` and `command.log` (what it said), `exitcode`, `workdir.txt`. For a step
   that *succeeded*, the same exact command is saved next to its results: every
   `results/.../log/` folder has a `<name>_command.sh`.
3. Common cases:
   - **Exit status 3** is a known data problem the pipeline detected. It is not
     retried, and the message says what to fix. Typical: a MACS3 target without a
     control; an empty BAM; a scale-factor multiplier missing or NaN (a sample absent
     from, or failing, its `norm_run`); orphan reads found after blacklist filtering;
     no bowtie2 index files at the `genome_index` prefix; a classification whose groups
     or `norm_run` do not fit.
   - **Startup errors** (before any step runs; they are at the end of the log) name the
     problem directly: unknown `control_id` or `norm_run`, duplicate `sample_id`, a
     missing file, both FASTQ and `bam` on one row, a `peaksets.csv` group that matches no
     sample, a target group that mixes antibodies, a resolved threshold that is not numeric,
     a classification whose groups or `norm_run` do not fit, an unknown region name or a
     region name that collides with a peak set, a script replacement path that does not
     exist, or a script key that names no pipeline script (the message lists the valid names).
   - **Launcher errors** (before Docker starts): a network path (`smb://`, `//server/share`), a
     folder or drive that Docker Desktop does not share or that is not connected, a samplesheet
     that is not in the project folder, an absolute path given for `outdir`, `metadata_dir` or
     `intermediate_dir`, a comma in a mounted path, free disk below 20 GB (see "Disk space"), or
     a budget below the about 5 GB the pipeline needs (the message says which limit to change).
   - **"Docker is installed but its engine is not running" / "Cannot connect to the Docker
     daemon"**: Docker Desktop is closed or still starting. The launcher starts it and waits up
     to 4 minutes; if it keeps failing, ask the user to open Docker Desktop, wait for "Engine
     running", and run again.
   - **Exit 137 / 140 / 143** (out of memory, or a signal): the step is retried
     automatically with more memory, within the budget. If it still fails, the budget is
     too small for this data: tell the user. A larger `max_memory_gb` cannot go above
     Docker's limit; raising Docker's Memory setting is the user's change (ask first).
     Real runs on the cluster peaked well below the budgets, so this points to unusual
     data or a small computer; say so.
   - **ChIPseqSpikeInFree aborts:** the pipeline never falls back to an old
     `_SF.txt`; check the step's log for the package error and the `norm_runs.csv`
     `bin_size`/`cutoff`/`max_turns` of that run.
4. Fix the input or config, then re-run `bash utils/run_cutandrun.sh run --detach`.
   Completed steps are reused.
5. If the failure looks like a bug in the shared pipeline rather than in this
   project's data or config, **tell the user and stop**. Don't patch the pipeline folder.

## Customizing this project's analysis or plots

Every step of the pipeline runs one script from `{{PIPELINE_DIR}}/bin/`. To
change a step for this project only, copy that script into `utils/`, edit the
copy, and add a `config.yaml` line **named after the script** (file name
without extension) with the copy's path. The shared script stays untouched for
everyone else.

```bash
cp "{{PIPELINE_DIR}}/bin/qc_alignment_plot.R" utils/                 # 1. copy
# 2. edit utils/qc_alignment_plot.R (keep Unix line endings: LF)
# 3. add to config.yaml:   qc_alignment_plot: utils/qc_alignment_plot.R
bash utils/run_cutandrun.sh run --detach                              # 4. only that step (+ downstream) re-runs

## Analyses beyond the pipeline (extra steps)

Analyses the pipeline doesn't do (a different statistical test, a custom plot, a
comparison across samples, ...) are allowed. The project's own scripts run through
the launcher's `script` command; the pipeline's own steps still run only with `run`.

**Convention**
- The script lives in `utils/<name>.<R|py|sh>` (`utils/` already holds this
  project's script replacements and extra steps).
- Its outputs go to `results/<name>/`: a **new** subfolder of `results/` named
  after the analysis, never one of the pipeline's own entries (`qc`, `bam`,
  `scale_factors`, `norm_qc`, `bigwig`, `peaks`, `classify`, `heatmaps`, `tracks`,
  `annotation`, `intersect`; see "Results").
- Inputs are the pipeline's outputs (e.g. `results/scale_factors/`, `results/bam/final/`,
  `results/peaks/csaw/`) or files the user provides (the user says where; never move
  raw data). The script reads them relative to the project folder and writes only to
  `results/<name>/`.

**Workflow**
1. Ask the user for the context and the question ("Ask about the experiment"
   applies); record it in `CONTEXT.md`.
2. `statistician` designs the analysis for anything statistical: method,
   assumptions, what the result can and cannot say.
3. `code-supervisor` (via `implementer`) writes `utils/<name>.*`.
4. The lead runs it: `bash utils/run_cutandrun.sh script utils/<name>.R [args...]`.
   The script must be inside the project folder; the interpreter follows the extension
   (`.R` Rscript, `.py` python3, `.sh` bash); the working directory is the project folder.
   It runs in the foreground, in the pipeline's image, with the same CPU and memory
   budget as `run`.
5. `log-inspector` reads `metadata/script_logs/<name>_<YYYYMMDD_HHMMSS>.log`: a header
   (date, project, script, md5, arguments, image and image ID, budget, working directory),
   the output, and a footer `-- exit code N --`. The launcher's exit code is the script's.
6. `results-reporter` and/or `figure-maker` (PNG) review the output.
7. `methods-writer` writes `results/<name>/METHODS.md`: the method, the tool and
   package versions (from the log header and the script) and the parameters.

Commit the script (`utils/` is tracked) after asking the user.

**Tier 1 (default): run it through `script`.** That uses the pipeline's image and its
memory limits, and gives a log. The image holds the tools the pipeline runs (for
example bowtie2, samtools, deepTools, MACS3, SEACR, pyGenomeTracks; see the table
under "Customizing") and the R and Python packages the pipeline's own scripts use
(for example csaw, edgeR, ChIPseqSpikeInFree). It is not known from this folder which
other packages the image holds: check with a short test script before relying on one.
Installing R or Python packages at run time is **not** allowed (not reproducible).

**Tier 2 (fallback): run on the host.** Only when the image lacks the needed tool
or package. Ask the user explicitly; if they agree, run it on the Mac with the
versions recorded (R `sessionInfo()`, `pip freeze` / `conda list`) in `results/<name>/`
and `CONTEXT.md`, and say in the Methods that it ran outside the pinned image.

Never install software system-wide, and never edit the pipeline folder, without
asking. The pipeline's own steps are still only run with `run`.

results/tracks/peak_qc/                                  the automatic peak QC tracks and their regions files (run_peak_qc with run_tracks)
results/annotation/                                      only if run_annotation
results/intersect/                                       only if run_intersect
metadata/nf_logs/                                        one log per run and last_run.status
metadata/script_logs/                                    one log per `script` run
```

When summarising results, start from `results/qc/report/<project_name>_qc_report.html`
and the MultiQC report; check `results/scale_factors/*.scale_factors.tsv`
(`qc_pass`, `note`) before interpreting any normalised track or peak set.

## Disk space

The launcher checks the free space on the project's volume before each run. It takes
the total size of the FASTQ and BAM files named in the samplesheet and expects about
5.6 times that much free (`disk_factor=5.6`, work files and results together, when the work folder is in the project folder; with the work volume the project's volume is checked against `disk_results_factor=1.0` for the results, and Docker's disk against about 4.6 times for the work files). It warns below that, and it stops before the
run below 20 GB free (`disk_hard_min_gb`, `docker/requirements.conf`). These multipliers are estimates pending the next run. Chromatin runs
need a lot of disk: the lab's estimate is about 100 GB or more per dataset, so check
before starting. To estimate, run this in the project folder (paths written with `~` are
skipped: write them out in full first):

```bash
tail -n +2 samplesheet.csv | cut -d, -f2-4 | tr ',' '\n' | grep -v '^$' \
  | while read -r f; do [ -f "$f" ] && du -kL "$f"; done \
  | awk '{ s += $1 } END { printf "%.1f GB of input files\n", s / 1048576 }'
```

The working files (`metadata/work/`, and the intermediate files in `intermediate_files/` with
`publish_intermediates: true`) and the results take the rest. `metadata/work/` and `metadata/.nextflow/` are kept by default (`keep_work: true`), so a
re-run only redoes what changed. Files in `results/` and `intermediate_files/` are
hard links to the files in `metadata/work/` when the disk allows, so big files are not
stored twice; never edit a published file in place.

To free space, once the user is happy with the results:
- `bash utils/run_cutandrun.sh clean` (ask the user first; it asks too): removes
  `metadata/work/` and `metadata/.nextflow/`. Results are kept; the next run starts from scratch.
- or `keep_work: false` in `config.yaml`: they are deleted after each successful
  run; re-running then recomputes everything.

Failed or stopped runs always keep them, so a re-run resumes.

## Subagents

The subagent definitions are in `.claude/agents/` of this project (copied there by `init`
when the pipeline has them). Delegate with the same table as `CLAUDE.md`; every task in
it goes to its agent:

| Task | Agent | Model |
|---|---|---|
| Messy input files (Excel/CSV sample sheets, `samplesheet.csv`, `norm_runs.csv`, `peaksets.csv`, collaborator or vendor tables) | `input-preparer` | sonnet |
| Reading: a question needing >2 files, or a file over ~300 lines | `scout` (several in parallel) | haiku |
| After every run, success or failure | `log-inspector`, then `results-reporter` on success | haiku |
| Comparing with earlier or collaborator numbers | `output-verifier` | haiku |
| Statistics questions and comparison or peak-set design | `statistician` | sonnet |
| Plots | `figure-maker` | sonnet |
| Analysis beyond the pipeline (see "Analyses beyond the pipeline") | `statistician` (design), `code-supervisor` (script), `log-inspector` (script log), `methods-writer` | sonnet / haiku |
| Methods text | `methods-writer` | sonnet |
| Edits to `utils/` scripts or project CSVs beyond a trivial fix | `code-supervisor` (spawns `implementer`) | sonnet |
| Writing or editing code that `code-supervisor` hands over | `implementer` | haiku |
| Outside facts (tool flags, library formats) | `web-researcher` | haiku |
| Papers and citations | `literature-scout` | sonnet |
| How csaw, edgeR, ChIPseqSpikeInFree or the pipeline code works | `code-researcher` | sonnet |

Rules for every subagent:

- Read-only in the pipeline folder `{{PIPELINE_DIR}}`; never edit `original_data/`, or any raw FASTQ or BAM.
- Never start, stop or clean a run, and never run a `script`: only the lead does that, with
  `utils/run_cutandrun.sh`. The Hard rules apply to subagents too (no `docker run`,
  `nextflow`, `bowtie2`, `samtools`, no `Rscript` or `python` on the computer).
- Files they change are in this project. Git is the backup: the lead commits after asking the user.

If the agents are not listed as available subagent types (e.g. the project was created
mid-session), either spawn a general-purpose agent whose prompt is the agent file's body
(after the frontmatter) plus the brief, with the model from the file's frontmatter, or ask
the user to restart Claude Code in the project folder (recommended for every later session:
start Claude Code inside the project folder, so it loads this project's `CLAUDE.md` and agents).

If `.claude/agents/` is missing, this project predates the kit: `init` of a newer pipeline version
creates it, or copy `{{PIPELINE_DIR}}/agent/.claude/agents` here (`cp -R`).
